# Release review v0.1.0

Diff reviewed: `v0.0.2..v0.1.0` (201 commits, 615 files, +68,875 / -22,196).
Effort: medium. Reviewed 2026-08-21.

**Verdict: fix-first.** The tag already exists on `main`, so this is not a gate on
cutting it - it is a gate on what may be *switched on* in it, and a work list for
`v0.1.1`.

Two of the worst findings are inert at default settings, and must stay that way until
they are fixed:

- **Do not set `repair.enabled=true` on v0.1.0.** Finding 1 can permanently destroy a
  segment that was fully readable.
- **Do not set `payout.auto-settle-enabled=true` on v0.1.0.** Finding 3 can mark a
  worker paid for money that never left the treasury.

Three more are live at default settings and are the case for a `v0.1.1`: the edge
process panic (5), the settlement-window poisoning (2), and the per-file resolve burst
(6).

## Blocking

### 1. Repair evicts live pieces below `RequiredShares` and permanently breaks the segment

`coord/repair/repairer/segments.go:400` (same defect in `repairClone`, line 501)

Repair unconditionally removes every unhealthy piece from the segment's piece list no
matter how many replacements were actually uploaded. Storj's
`healthyAfterRepair >= OptimalShares` guard is missing: it only strips all unhealthy
pieces when the post-repair healthy count reaches optimal, otherwise it strips only the
unretrievable ones.

*Failure:* RS(29/52/60/80) segment, 60 stored pieces, 40 classified unhealthy (clumped /
out-of-placement / suspended worker) but all still readable, so healthy = 20.
`FindStorageNodesForUpload` returns 3 fresh workers, so `added = 3` and the
`len(added) == 0` early-out does not trip. The new list written to the DB is
20 + 3 = 23 pieces, discarding 40 live readable pieces. 23 < RequiredShares(29): the
segment is now irreparable and undownloadable, though every byte was online a second
earlier.

*Fix:* restore the `healthyAfterRepair >= OptimalShares` condition before removing
unhealthy-but-retrievable pieces.

*Mitigation today:* `repair.enabled` defaults to `false`.

### 2. One malformed first order poisons the whole settlement window

`coord/order/settlement.go:133`

The window is taken from the first stream entry's `limit.OrderCreation` at line 135,
before `verifyOrder` runs at line 160. A first entry with a bad coordinator signature
still fixes the window.

*Failure:* a worker sends a first `{limit, order}` pair whose `OrderCreation` is some
other hour and whose signature is invalid. Every subsequent genuine order for the real
hour then fails `!window.Equal(orderWindow)` at line 137 and is skipped. `amounts` stays
empty, the store is never called, the response is `STATUS_REJECTED`. The hour's settled
bandwidth is never credited - the worker is not paid and the customer's egress is never
billed - and the worker's retry reproduces it forever.

*Fix:* validate the first entry before deriving the window from it, or derive the window
only from an entry that has passed `verifyOrder`.

### 3. `EthSender` ignores `IdempotencyKey`, so batched payouts can collide on a nonce

`coord/payout/ethsender.go:137`

Each payout derives its nonce from a fresh `PendingNonceAt` and ignores
`req.IdempotencyKey`. `sender.go:267` states that an implementation able to derive a
deterministic nonce from the key MUST do so.

*Failure:* `AutoSettler.RunOnce` calls `settleOne` sequentially. If the txpool has not
yet reflected the previous transaction (mempool lag, or the RPC endpoint is a load
balancer over several nodes), payout B gets A's nonce. A 1 wei rise in
`SuggestGasPrice` between the calls makes B a valid replacement, so A is evicted and
never mined. Both rows are already `settling`, both have a `broadcast_tx_hash`, and both
have become `worker_payments` rows - worker A's ledger says paid, its reservation is
released, and it never received the money. Only an on-chain reconciliation nobody runs
would detect it.

*Fix:* derive the nonce deterministically from `IdempotencyKey`, per the `Sender`
contract.

*Mitigation today:* `payout.auto-settle-enabled` defaults to `false`.

### 4. A `settling` withdrawal can never be released, and it holds the worker's one-pending slot

`coord/db/withdrawal_repo.go:672`

`ResolveWithdrawal` filters on `status = 'pending'`, but `pendingStatuses` and
`idx_worker_withdrawals_one_pending` both include `settling`.

*Failure:* `AutoSettler.recoverFromSendFailure` deliberately leaves a row `settling` when
`ReturnToPending` refuses it (a hash was recorded), or the process dies between
`MarkSettling` and `RecordBroadcast`. `coord compensation withdrawals reject <id>` then
returns `ErrWithdrawalNotPending`. The worker is permanently blocked from any new
withdrawal, and the operator's only remaining action is `settle`, which writes a
`worker_payments` row for money that may never have left. There is no operator path to
release a `settling` reservation.

*Fix:* let `ResolveWithdrawal` (or a dedicated operator command) act on `settling`, with
the tx-hash caveat surfaced.

### 5. Edge process panics on `send on closed channel` and takes every in-flight download with it

`edgeserver/readahead.go:211`

`readAheadWriter.close()` does `handOff()` then `close(w.ch)` with no guard against a
later `Write`. There is no `closed` flag; `w.err` is only consulted, never set to a
sentinel on close.

*Failure:* `serveFull` calls `raClose()` as soon as
`s.client.DownloadManifest(ctx, m, ra)` returns. The go-sdk fans a download across
per-piece goroutines; if any of them (or a retry path) writes into `ra` after the
top-level call returned - e.g. a timeout/cancel unblocks the caller while a decode
goroutine is still draining - `handOff`'s `w.ch <- buf` panics. A panic in a
non-request goroutine is not recovered by `net/http`'s per-request recover, so it kills
the edge process for every concurrent download, not just this one.

*Fix:* set a `closed` sentinel in `w.err` under the same lock `handOff` takes, and make
`Write` return that error instead of sending.

## High

### 6. Per-file download-resolve burst of 3 sheds a hot object instead of collapsing it

`coord/file/service.go:73`

`ratelimiter.NewRateLimiter` builds `rate.NewLimiter(1000/s, burst=3)` and `IsAllowed`
calls `Allow()`. A token bucket cannot admit more than `burst` in one instant no matter
the refill rate.

*Failure:* 50 viewers request the same HLS segment within the same millisecond - the
exact case the download-data cache was added for. 3 resolves are admitted; 47 get
`codes.ResourceExhausted`, which `writeResolveError` maps to HTTP 503.

The config comment claims "at 1ms/burst 3 it allows ~1000 resolves per second for one
file" and that "collapsing a hot object is strictly better than rejecting it". The
second half is the design intent; the code does the opposite. Enabled by default
(`file.download-object-rate-interval` = 1ms), so this ships on.

*Fix:* raise `file.download-object-rate-burst` substantially, or gate the limiter behind
the cache so collapsed resolves do not each consume a token.

### 7. The accrual watchdog is blind to roughly 48h of egress

`coord/periodclose/watchdog.go:124`

`PriceClientsUntil(..., p.StartDate(), now)` reaches `QueryContractPeriodUsage`, whose
egress is `SUM(egress_settled) + SUM(egress_inline)` (`accounting_repo.go:1140`). A
worker cannot offer an hour-window for settlement until ~`accounting.SettlementHorizon`
(~49h) after it opens - the same lag `schedule.go:179` refuses a shorter grace-delay
over.

*Failure:* on every pass the watchdog sees zero egress for the last two days. An account
with a $5 overdraft allowance can pull unbounded egress for 48+ hours past its balance
before `projected()` moves at all, and the network has already paid workers to serve it.

The type's doc claims the only bias is "the newest tally snapshot contributes nothing
until another arrives" - that understates the real lag by two orders of magnitude, and
describes storage, not egress.

*Fix:* price the watchdog off `egress_allocated` (which is recorded at manifest issue)
rather than `egress_settled`, or add allocated-minus-settled as an accrual estimate.
Enabled by default (`period-close.watchdog.enabled`).

## Medium

### 8. Contract egress `allocated` and `settled` land in different hour buckets

`coord/file/endpoint.go:1039`

`recordDownloadBandwidth` passes wall-clock `time.Now()` to `AddContractEgress`, which
truncates to the hour. The settled side (`addContractEgressSettleTx`, via
`AddWorkerBandwidthSettleWithWindow`) uses `limit.OrderCreation.Truncate(time.Hour)`. A
manifest minted at 10:59:59.9 records allocated into hour 11 (if `now` crosses over
during the segment loop) and settles into hour 10, so per-hour
`egress_allocated - egress_settled - egress_dead` is wrong in both directions at every
boundary. `Allocation.Record` (`allocation.go:142`) avoids wall-clock for exactly this
reason; the contract side did not get the same treatment.

### 9. `MaxBackfillPeriods == 0` closes the newest due period over unclosed older ones

`coord/periodclose/schedule.go:334`

Documented as a legal policy ("missed periods handled by hand"). With 2026-06 and
2026-07 unclosed and 2026-08 becoming due, `due` is `[06, 07, 08]` and the function
returns `[08]`. `closeWorkerHalf(2026-08)` then runs `compensation.GenerateStatements`,
whose withheld-bond release reads the lifetime paystub balance from `worker_paystubs` -
a ledger now missing two months. Bond is released against the hole, and it repeats every
month because the older periods stay due forever.

Contradicts `RunOnce` line 128 ("Stop rather than skip ahead...") and `DuePeriods`' own
"OLDEST FIRST IS LOAD-BEARING" header.

### 10. `RecordBroadcast` reports a no-op update as success

`coord/db/withdrawal_repo.go:151`

The UPDATE is guarded on `status = 'settling'` but `RowsAffected` is never checked, and
`res.Error` is nil for zero rows. If the status changed between `Send` returning and this
call (a concurrent operator, or a second settler), `settleOne` proceeds to
`SettleWithdrawal`, which accepts any status that `HoldsReservation()`, and the row ends
`settled` with `broadcast_tx_hash = ''` - the exact "settling row with nothing on it"
that the mark → broadcast → record ordering exists to prevent. `ReturnToPending`, ten
lines below, does check `RowsAffected` for the same race.

### 11. The download-data cache loader closes over the first caller's cancellable context

`coord/file/service.go:497`

`buildManifest` wraps ctx with `DownloadResolveTimeout` (10s default) before calling
`LoadDownloadData`. lrucache runs `load` under `state.once`, so N concurrent resolves of
one object all block on the first caller's `fn`.

*Failure:* the first caller's HTTP request is cancelled mid-load - an aborted range
request, a player seeking, routine on this path. `store.GetByID` returns
`context.Canceled` and every waiter gets it, returning 500/502 to their own still-live
clients. The failed entry is dropped so the next wave retries, but every disconnect
during a load takes out the whole in-flight batch, and the first request's 10s deadline
bounds all of them.

### 12. Download candidate trimming can discard the live holders

`coord/order/downloadnodes.go:85`

`SelectDownloadCandidates` cuts candidates to `required + tail` with a blind
`rand.Perm` over a snapshot whose liveness and disqualification are applied only at
selection-cache refresh time (`endpoint.go:1164-1167`).

*Failure:* on RS(29/52/60/80), 80 locations are cut to 38. If 12 holders went down since
the last refresh and the permutation keeps 10 of them, only 28 of 38 limits reach a live
worker and the download fails below `RequiredShares` - with 42 live holders discarded
unselected. The function's doc names the hazard but only acts on it in the
non-over-provisioned case; the over-provisioned case is production.

### 13. Unvalidated gRPC metadata is written straight into structured logs

`internal/grpcutil/log.go:161`

`correlate` copies caller-supplied metadata into zap fields with no length, character-set
or newline validation, on every unary and stream RPC of both coordinator and worker.

*Failure:* any peer sends `x-aioz-download-id: <64KB containing newlines and forged JSON
log lines>`. It is logged verbatim as `zap.String("download_id", ...)` and, in the
worker, latched onto the per-request logger (`piecestore/endpoint.go:909`) so it repeats
on every line of that download. With logship enabled it is forwarded to Loki, so a
hostile worker or client can inject forged log records and inflate log volume without
bound.

*Fix:* bound the value (e.g. 64 chars) and restrict it to hex/base64 before logging. It
is only used for correlation.

## Low

### 14. `TrackConns` returns a typed-nil, contradicting its own doc

`internal/grpcutil/conntrack.go:40`

The comment says "It returns `lis` unchanged if `lis` is nil, so callers can wrap
unconditionally", but it returns a nil `*TrackedListener` wrapped in a non-nil interface.
A caller following the doc gets `l != nil`, `grpc.Serve(l)` calls `Accept()`, and the nil
receiver's embedded `l.Listener` panics. Both current call sites compare against the
concrete type before assigning, which is the only reason it has not fired.

### 15. Object metadata headers survive onto pre-first-byte error responses

`edgeserver/handler.go:202`

`serveFull` applies stored system headers and user metadata before the transfer is
attempted. If the transfer fails before the first byte, `writeDownloadError` calls
`http.Error`, which deletes only Content-Length and overrides Content-Type - every other
header (Cache-Control, Content-Disposition, `x-amz-meta-*`) survives onto the
402/502/503/504. Previously the sink was driven by the SDK during the transfer, so an
early error carried none of it. A CDN acting on `Cache-Control` from an error response
now attributes the failed object's metadata to an error body.
