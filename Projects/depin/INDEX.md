- [[plans/2026-09-07-transcode-build-plan|Transcode build plan (depin server side)]] - the executable 8-phase plan the design spec lacked, approved 2026-09-07. Scope is depin server side only (protos, coord, worker, testplanet e2e); go-sdk and client-side tier-2 verification are follow-ups because go.mod pins go-sdk to a remote pseudo-version. Decisions: reuse hub's ideas but write all code in the depin tree, transcode gets real config/rendition/session tables (the storage_configs precedent the spec cites was dropped by migration 000029 and does not transfer), and ffmpeg is a subprocess not cgo so the CGO_ENABLED=0 cross-compile matrix stays green. Two things the spec missed: TRANSCODE must be added to the paidActions whitelist in coord/order/settlement.go or every settlement silently fails, and used_for_transcode takes DiskSpace field 12.
- [[2026-08-28-transcode-as-a-service-on-depin|Transcode-as-a-service on depin]] - depin provides transcode compute only: the client segments the source and assembles the manifests, depin holds the ladder as a transcode config on a TRANSCODING-type contract (the enum value already exists, unused), selects capable workers, and authorizes each segment with a coordinator-signed OrderLimit carrying the compute budget so metering falls out of the existing settlement path. Async submit/poll/fetch with worker-local output under TTL sharing the worker's storage allocation; verification is client-side tier-1 checks plus sampled MPEG-7 signature redundancy, which avoids the self-reported-measurement flaw found in both go-livepeer and hub.

- [[2026-08-09-git-release-flow|Git flow + pre-merge-only CI validation]] - adopt `feature/* -> develop -> release-X.Y -> main -> tag`, and stop re-running lint/test on `main` and tags. The trigger was "why re-test on merge to main", and the answer turned out to be that it IS redundant here: `main` has zero non-merge commits outside develop and `git diff main develop` is identical, so every merge re-validated a byte-identical tree. Storj does the same thing - its pre-merge Jenkinsfile (317 lines) runs everything, its post-merge Jenkinsfile (159 lines) runs build+publish and no tests - and its release branches show why `release-X.Y` is needed at all: v1.99.0-rc and v1.99.3 share one cut point with 15 fix commits over 9 days while trunk kept moving, which is exactly our staged-rollout window. Branch protection + "pipelines must succeed" become the ONLY gate once validation leaves `main`, so they are a hard prerequisite. Also: no `hotfix/*` branch type (it matches nothing in `workflow.rules` and would build nothing - recreate `release-X.Y` from the tag instead), a `check:backmerge` job for Git Flow's classic lost-fix failure, and cache key split (go.sum-keyed modules + fallback_keys) since `main` was recompiling the cosmos tree cold every merge. Phase 1 (docs: `docs/BRANCHING.md` + RELEASE.md §2/§4/§11) is done; Phase 2 (the CI rule changes) is not started. Merge trains would supersede this but are Premium and gitlab.internal is CE.
- [[2026-08-05-docker-bake-multiplatform-release-cicd|docker bake multi-platform release + GitLab CI/CD]] - replaces the host-build + `docker save`/scp flow with a `docker buildx bake` graph: `PLATFORMS` map as the single source of truth, Zig as the C cross-toolchain (cgo is unavoidable - go-ethereum's libsecp256k1 has no pure-Go path), statically-linked musl linux binaries that retire the glibc-2.39 image pin, multi-arch images with SLSA provenance + SBOM, cosign signing, and a GitLab pipeline. Shipped: linux/amd64+arm64, windows/amd64, freebsd/amd64. macOS needs a NATIVE runner (Zig has libSystem but not Apple's frameworks); linux/arm is blocked upstream (go-aioz `x/mint/simulation/genesis.go:24` overflows a 32-bit int). Scope grew to split `relay` and `jobq` out of the coord binary after finding they inherited coord's root `--identity-dir` and so defaulted to the COORDINATOR's peer ID. See the 'As built' section for the deltas, open items, and the one genuinely failing test.
- [[2026-08-06-segment-verify|segment-verify (manual segment health checking)]] - standalone `cmd/segment-verify` binary ported from Storj `cmd/tools/segment-verify`: probes every holder of a segment with a 1-byte `Download` under a GET_AUDIT order limit and reports found / not-found / offline per piece. Read-only (no reputation writes, no repair enqueue). Bulk `run range|contracts|read-csv` with Storj's CSV outputs, plus targeted `check segment|file|contract` with a table and verdict exit code; handles RS and CLONE (CLONE threshold is 1). Library in `coord/segmentverify/`, queries reuse `auditSegmentScan`, probe reuses `audit.NewDialFetcher` + `ClassifyFetchError`. Key traps documented: order limits MUST be minted per probe (usedserials keys on coordinator+serial only, so a per-segment serial breaks the moment two pieces share a worker), `err == nil` with 0 bytes is not success, concurrency defaults to 64 not Storj's 1000 because of the shared-relay `MaxConnsPerIP` cap, and the revocation DB must default to `memory://` or the bolt flock collides with a live coordinator
